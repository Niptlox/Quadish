# Сигнальная сеть: план оптимизации + дистанционный передатчик

Два вопроса про уже реализованную сеть (провод/рычаг/лампа/вентили НЕ/И/ИЛИ
поверх активаторов, `units/Objects/TileClasses.py`): как не упереться в
производительность при больших схемах, и как сделать беспроводную связь
между двумя точками карты. Это план/концепт, не код — реализация отдельным
шагом.

## 1. Оптимизация до уровня "компилируемости"

### Текущая модель и её реальная стоимость

Сейчас каждый сигнальный тайл с `CLASS_UPDATING_TILES` (рычаг/лампа/вентили)
опрашивается **каждый кадр, для каждого видимого на экране тайла**
(`ScreenMap.update_tile` вызывает `.update()` только у тайлов в кадре — это
уже естественно ограничивает нагрузку размером экрана, а не размером мира,
так же как сейчас работают Furnace/Activator). Внутри каждого вызова:

- вентиль делает `count_active_neighbors` — 8 обращений `get_tile_and_obj`
  (чанк-словарь + срез массива тайла) **каждый кадр**, даже если ни один
  сосед не менялся уже 10 минут;
- `bfs_activate` из провода в провод — обход всей связной сети целиком за
  один синхронный вызов (уже быстро для одиночного события, но не
  переиспользует топологию между вызовами — каждый раз считает заново).

Для десятков тайлов в кадре это незаметно. Для сотен (большая ферма
триггеров/крупная логическая схема, вся на экране сразу) — заметный,
хоть и не катастрофический, налог на каждый кадр, который не проходит,
даже если схема физически не менялась.

### План оптимизации (по возрастанию сложности/выгоды)

**Шаг 1 — событийная модель вместо опроса каждый кадр (главный выигрыш).**
Вентиль должен пересчитываться не "каждый кадр, пока виден", а только
когда **реально изменился один из его входов**. Механизм: у `GameMap`
появляется `dirty_signal_tiles: set[(x,y)]` — множество координат, которые
надо пересчитать на этом такте. `bfs_activate`, вместо того чтобы просто
touch'ать `activated_tact`, при **смене** состояния тайла (было
неактивно → стало активно, или наоборот) добавляет его СОСЕДЕЙ-вентили в
`dirty_signal_tiles`. Каждый тик игры обрабатывается только это множество
(обычно пусто или единицы элементов), а не все видимые вентили. Статичная
схема — стоит 0 на такт вместо N вентилей × 8 соседей.
Требует: вентили перестают полагаться на "меня вызовут каждый кадр", а
явно планируются через `dirty_signal_tiles`; `Lever`/`PressurePlate`
добавляют себя в dirty-множество при смене `on`/`pressed`, а не дожигают
сеть каждый такт вручную (сейчас это единственное, что держит сеть "живой"
непрерывно — с dirty-моделью это становится не нужно).

**Шаг 2 — "компиляция" длинных проводов в одно ребро.**
Пока топология не менялась (никто не сломал/не поставил `Wire`/`Activator`
рядом), длинная цепочка проводов между двумя функциональными узлами
(источник → вентиль/лампа) всегда даёт один и тот же результат обхода.
При первом обходе после правки мира — кэшируем в `GameMap.signal_edges:
dict[node_id, list[node_id]]` уже "сжатую" сеть: конечные узлы (не-провода)
напрямую ссылаются друг на друга, минуя провода между ними. `bfs_activate`
для скомпилированной сети превращается в обход по `signal_edges` — O(число
функциональных узлов), а не O(число тайлов провода). Инвалидация кэша — по
чанку: `set_static_tile` уже помечает `modified_chunks`, туда же добавляем
пометку "пересобрать signal_edges для этого чанка при следующем обращении"
(ленивая переcборка, не на каждую правку).

**Шаг 3 (опционально, если Шаг 1+2 всё ещё мало) — топологический порядок
внутри такта.** Сейчас у вентиля есть допуск в 1 такт (это и есть неявная
"цена" за то, что порядок обновления тайлов на кадре не гарантирован).
Если урожай схем игроков вырастет до сложных многослойных цепочек, можно
посчитать топологический порядок вычисления (кто от кого зависит) один раз
при компиляции (Шаг 2) и обновлять вентили в этом порядке за один проход —
тогда сигнал распространяется мгновенно за 1 такт на всю глубину схемы, без
допуска, и без лишних пересчётов. Это самая "настоящая компиляция", но и
самая инвазивная правка — делать только если шаги 1-2 недостаточно.

**Что НЕ делать:** не пытаться сделать полноценный тикающий движок с
очередями отложенных событий (как в Minecraft redstone) — это на порядок
больше кода ради эффекта, который для этой игры (2D-песочница, не
специализированный редстоун-симулятор) не оправдан. Шагов 1-2 достаточно,
чтобы статичные схемы почти ничего не стоили, а активность схемы стоила
пропорционально числу реально сработавших узлов.

## 2. Дистанционный передатчик (беспроводная пара)

### Идея

Вместо числового "канала/ID" (не вписывается в визуальный, без-менюшный
стиль игры) — переиспользуем уже знакомый игроку паттерн из **Шкафа**
(индекс 126, `ITEM_WITH_STATE_IS_LIST`): 4 предметных ячейки (2×2 сетка),
куда можно положить любые предметы. Комбинация из 4 предметов — это и есть
"частота". Передатчик и Приёмник с одинаковой комбинацией связаны, с
разной — не видят друг друга. Интуитивно: "настроить рацию" — положить
одинаковые 4 предмета в оба блока, прямо как выставить те же 4 иконки в
шкафу, а не вводить код в текстовое поле.

Рация должна работать только **в пределах определённой области**, а не по
всей загруженной карте — иначе это не "дальняя связь", а телепорт сигнала
в любую точку мира без всякого компромисса, что и не похоже на рацию, и
ломает баланс (мгновенная детонация далёкого динамита без физического
провода вообще без ограничений). Радиус — фиксированная константа
`TRANSMITTER_RANGE` (по аналогии с `CHUNK_CREATURE_LIMIT`/другими
игровыми константами в `units/common.py`), порядка 3–4 чанков
(`TRANSMITTER_RANGE = CHUNK_SIZE * 4`, т.е. около 128 тайлов) — хватает на
"всю обжитую базу", но не на весь мир. Если понадобится усиливать сигнал —
естественное расширение на будущее (не в этой итерации) — отдельный блок
"антенна", повышающий `TRANSMITTER_RANGE` для конкретного передатчика.

### Блоки

- **Передатчик (Transmitter)** — новый `SignalTile` + `ACTIVATE_TILES`
  узел, с `Inventory([2, 2])` как у Rack (переиспользуем класс `Inventory`,
  `units/Inventory.py`, тот же 2×2 layout и рендер, что уже есть у 126).
  `view_interface_on_click = True` — правым кликом открыть те же 4 ячейки.
  Ведёт себя как обычный узел сети (провод/активатор могут в него
  "затекать" через `bfs_activate`), но ДОПОЛНИТЕЛЬНО: как только сам
  становится активным (его коснулся `bfs_activate`), смотрит на свою
  4-предметную комбинацию и удалённо активирует все загруженные Приёмники
  с такой же комбинацией — без физического провода между ними.
- **Приёмник (Receiver)** — тот же `Inventory([2, 2])` для комбинации,
  тоже `ACTIVATE_TILES` узел (чтобы то, что он получил, могло продолжить
  сеть дальше через обычные провода/лампы). Сам по себе пассивен — просто
  цель для передатчиков с совпадающей комбинацией.

### Механизм совпадения без сканирования всего мира

Перебирать все загруженные объекты каждый раз, когда сработал передатчик
— расточительно. Вместо этого `GameMap` держит индекс:
`self.signal_receivers: dict[tuple, set[Receiver]]`, ключ — комбинация
(нормализованная: `tuple(sorted(item.index for item in slots if item))`,
чтобы порядок раскладки по ячейкам не имел значения). `Receiver` регистрирует
себя в этом индексе при создании/при изменении содержимого ячеек (событие
инвентаря, `items_update_event` — уже есть в `Inventory`, используется у
Furnace) и снимает регистрацию при разрушении блока (`items_of_break`/аналог
деструктора, по образцу того, как `Chest`/`Furnace` уже освобождают свои
ресурсы).

`Transmitter.fire()`:
```python
for r in game_map.signal_receivers.get(self.code(), ()):
    dx, dy = r.tx - self.tx, r.ty - self.ty
    if max(abs(dx), abs(dy)) <= TRANSMITTER_RANGE:  # тот же tx/ty, что у Tile
        bfs_activate(game_map, r)
```
Комбинация уже сужает перебор до горстки совпадающих приёмников по всему
миру (обычно 0-2), поэтому проверка расстояния поверх неё — копеечная
добавка, не отдельная пространственная индексация. Если бы диапазон
совпадений был большим (частая комбинация вроде "1 доска"), для будущей
оптимизации индекс можно дополнительно бить по региону чанков — но пока
не нужно, обычная практика игрока — использовать редкие/специфичные
предметы под частоту именно чтобы не пересекаться с чужими рациями.

### Ограничение (сознательное, не баг)

Приёмник должен быть **загружен** (в памяти, чанк не выгружен динамическим
дампом — см. уже существующий `dynamic_dump`), чтобы сработать — это
совпадает с тем, как уже ведёт себя вся остальная логика тайлов в игре
(Furnace не готовит еду в выгруженном чанке), и не требует придумывать
отдельный "фоновый" механизм для невидимых частей мира.
